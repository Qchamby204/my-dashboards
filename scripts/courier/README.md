# Courier publication and playback

Courier remains at `courier.html`. Atlas links to this original dashboard.

## Publication

An independent weekday timer wakes the workflow, with GitHub cron as a backstop. An automatic run creates an edition when that date is absent, or repairs only missing sections and missing narration in an existing edition. It then publishes audio, commits the manifest, requests a Pages build, and checks the public manifest and every advertised audio file. The backstop still performs the public checks when generation is skipped.

This explicit Pages request is necessary because [commits made with GITHUB_TOKEN do not trigger a Pages build](https://docs.github.com/en/actions/concepts/security/github_token). It uses the existing repository token with `pages: write` and the [Pages build endpoint](https://docs.github.com/en/rest/pages/pages#request-a-github-pages-build). It does not change the site's audience or publishing source. A run cannot report successful publication merely because its commit or build request succeeded.

Generation failures fail the run. Partial editions retain readable sections and report the audio/text-only counts in the workflow summary. Unavailable audio or a stale live manifest makes verification fail after bounded retries. No content is regenerated by those retries. GitHub can delay scheduled execution; this workflow does not promise an exact delivery time.

New audio URLs include their audio commit SHA, so a same-day rebuild cannot reuse a CDN URL for different bytes. Existing archive URLs remain intact. Publication runs are serialized. Manifest commits rebase onto current main so unrelated edits made during generation are preserved; conflicts fail visibly.

For delivery recovery, run **The Courier daily briefing** with **publish_only** selected. That republishes and checks the latest existing edition without model or voice calls. Leaving it unselected retains the manual rebuild behavior. Changes to the workflow or publication helper on main automatically perform the same publication-only check.

## Independent daily trigger and bounded recovery

A separate ChatGPT automation, **Courier daily delivery**, checks at 05:17 Winnipeg time and hourly through 11:17 on weekdays through the existing GitHub connection. It updates only `courier/daily-trigger.json` on `main`, using the current blob SHA. This push signal starts Courier independently of GitHub's cron scheduler. It introduces no new API keys or Atlas runtime behavior. It replaces the former automatic recovery task in place, rather than adding a competing timer. See [automation.md](automation.md) for its full execution contract and publication proof requirements.

The daily signal contains `schemaVersion: 1`, the Winnipeg edition `date`, an ISO `requestedAt` timestamp with a timezone, and `attempt` (1 through 3). The checked-in null signal is inert. The checker sends at most three signals per weekday, waits while Courier is active, and is silent once today's exact edition is verified. The repository chooses missing sections; the external timer cannot supply a repair list. It must not treat a successful signal write as publication. The existing morning status notification remains separate.

`courier/automatic-state.json` enforces a shared maximum of **three automatic generation attempts per local weekday**, including the initial build, repairs, failed builds, reruns and delayed cron backstops. Before any model/voice call, the locked workflow commits and pushes an attempt reservation. A failed reservation stops generation; a later generation failure cannot erase the reserved attempt. Publication-only checks do not consume generation attempts. Exhaustion is visible in the job summary, and available content can still be published and verified. The ledger is not a push trigger, so it cannot create a workflow loop. Do not reset it to obtain another automatic attempt.

All runs share the existing `courier-publication` concurrency lock. After acquiring it, the workflow checks out current `main` and rechecks the manifest and attempt ledger. It reads a push signal from the triggering commit, so a delayed event cannot borrow a newer signal's date. Daily signals automatically repair only current gaps. Signals for another Winnipeg date, a weekend, more than three hours old, or before 05:17 are ignored. Invalid signals and corrupt editions fail visibly. Normal publishing-code pushes cannot generate content. Manual rebuild and publication-only controls remain available.

`courier/recovery-request.json` remains an explicit manual fallback with its existing bounded attempt/date/age validation. A manual request without sections generates only an absent edition; an existing edition is preserved and republished/verified. An explicit sections request fills only those gaps. It can be used after investigating an exhausted automatic budget. The daily timer must not edit this file.

Generation and recovery use `America/Winnipeg`, including daylight saving changes, and the chosen date is passed into the builder. Both independent and GitHub timers still depend on their services being available; the check reports access failures, exhausted attempts, failed runs and unverified publication instead of claiming success.

Regression coverage includes independent ticks, queued duplicate ticks, delayed cron, partial repair, the shared cap, durable reservation failures, DST/weekday boundaries, malformed data, event-commit signal selection, and unchanged manual fallback. These synthetic tests make no model or voice calls.

Manual recovery requests may include `"sections": ["markets", "sports"]`, or any other expected section IDs, to fill missing sections or retry audio from their saved scripts. Finished sections are never replaced. The shared expected-section list includes weekday Lessons and all configured news sections; the front page is retired. Requests reject unknown or duplicate IDs. The independent timer and scheduled backstop can repair remaining gaps within the automatic budget.

### Why the trigger changed (September 2026)

Run #89 was created by a recovery push at 10:42 UTC on September 29; it built and verified the complete edition. Scheduled runs #90 and #91 were only created at 16:31 and 17:00 UTC and reused that edition. September 28 showed the same delayed event creation. This is upstream scheduling delay, not the concurrency lock blocking generation. On September 25, #81 generated while #82 and #83 only repeated publication verification. The external task also retained obsolete front-page expectations. The fix uses the already available independent timer as the primary wake-up, corrects its completion criteria, and moves repair selection and a durable cost bound into the repository. Adding another GitHub cron alone would retain the same failure dependency.

Repairs merge new audio into the existing day, preserve previous immutable URLs and scripts, and keep lesson progress and listening identifiers. Missing Lessons are reconstructed without advancing curriculum progress; a text-only Lessons section reuses its saved script and lesson metadata. Failed sections do not prevent other successful repairs from being saved.

The public `courier/status.json` records Updating before generation and Complete or Partial only after the exact live edition and every advertised audio file pass verification. Missing sections and text-only audio prevent Complete. The status record binds to the edition timestamps and exact audio URLs; the dashboard rejects stale proof. Failed runs report an interrupted update, and Updating expires after 90 minutes. Refresh checks for newly published content while preserving listening history. Status publication uses the same serialized workflow and current repository credentials.

If research exhausts its response budget before producing a usable script, each news section gets one writing retry with web tools disabled, using the already supplied feeds and newsletters. The builder records failed sections in new editions instead of leaving that information only in logs.

### Partially duplicate sections

The generated-section gate still checks cited stories and talking points against earlier accepted sections. Material overlap now triggers one deletion-only edit of the existing draft, replacing the former search-enabled rewrite. The editor returns paragraph, citation and talking-point indices with a 2,000-token output cap and no web searches. It cannot introduce replacement prose, new sources or padding. Local checks remove known repeated paragraphs (including mixed fresh/repeated paragraphs), citations and talking points, and reject malformed selections. Retained passages keep their original wording and source attribution; unused citations are removed. A distinct newsletter story can survive even if the planner missed it.

The shortened section is checked again before narration. A usable fresh remainder stays published and expected; an empty or still-duplicate remainder is skipped. An edit failure remains isolated to its section. Adaptive thin-news skipping, the initial duplicate thresholds, source collection limits and cross-edition story memory are unchanged. `duplicateRepairs` records `method: trim-existing-draft` plus the before/after overlap metrics. No extra research or length-repair pass follows the trim.

The September 30 regression reproduces one repeated source out of ten and three repeated talking points out of five. It verifies that fresh attributed climate passages survive, repeats do not, and climate remains in the edition's expected sections. Additional cases cover fully repeated content, mixed paragraphs, invalid selections, an unplanned newsletter story, quiet-section skipping and isolated editor failure. These use synthetic text and mocked editing/narration, not paid generation.

## Player

Section cards show duration text without decorative length gauges. Actual playback progress remains in the player. “Put it into practice” is collapsed initially, opens from its heading or a direct practice link, and retains its expanded state during saving and rerendering.

The original player uses one audio element across sections. Failed audio is reloaded when Play is retried. Continuation skips text-only sections, follows the saved preference, and reports a manual Play action if the browser blocks continuation. Play all explicitly starts the edition again; Resume listening continues an unfinished section in the selected edition.

Measured durations are kept with browser-local listening history and keyed by the actual audio URL. Queue time remains labelled approximate until every remaining audio length is known. Changing playback speed adjusts listening time remaining. No new account or sync service is involved.

[Media Session](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API) supplies section metadata, playback state, elapsed position, play/pause, Next and seek actions when supported. Browser and iOS behavior varies; this is not a native Live Activity. Unsupported actions leave the page controls working normally.

The publication test invokes the standard-library Python tests in `scripts/courier/tests`. These checks make no generation calls and send no notifications.
